architecture
============

Surrendering control of the controller makes it hard to enforce any
constraints. For example, suppose the UI has a button called "Foo" and
a corresponding click handler called doFoo(). The programmer must take
the initiative to notice whether there are any program states in which
executing doFoo() violates a constraint. Then, the programmer must
arrange to prevent the effects of doFoo() when entering such states
and re-enable it when exiting such states.  Since the program state is
implicit and spread across many mini-tasks, it is hard to be sure all
such constraints have been enforced, even when the job is well-defined
and has the programmer's full attention.

Forcing all events through centralized, state-based code inverts the
problem. Now, no events get acted on in a given state without explicit
code to permit it. One must opt in to reentrancy bugs rather than the
more daunting task of opting out.  Program state (at least in regards
to control flow) is explicit and visible.  Flow-of-control bugs are
less likely to be subtle and distributed and more likely to be an
obvious failure to handle a valid event, a failure whose location in
the code will likewise be obvious.

Design: rendering
=================
In read-mode, we want to display code nicely, the problem of pretty-printing.
Unfortunately, this is made harder than usual because of the fact that we
are displaying fragments of code, not entire units. It's not always possible,
for example, when looking at just a Javascript fragment to know that it
is actually inside of a class declaration.

Actually, it's worse than that (unsolvable?) because the same fragment
could appear in more than one context. (Although, it really shouldn't
appear in more than one *language* context. That is, it's either HTML,
CSS, or Javascript.)

I need the "output" window (an HTML rendering) to look identical to the
"other" window (a generated HTML page). At least, in "shape". Obviously,
the "output" window can have all sorts of syntax coloring, etc, but the
line breaks at least must be the same so that the user can track errors
back to their source. So, rendering to these two outputs is very similar.

Do I really need three "flavors" of code, or can I treat this is one
big language that changes syntax significantly in three different
places of the grammar? If I require you to reference a code fragment
before you define it, then I can (almost) always infer what language
the code fragment is using without an explicit user action.

If we know the current indent level before every call to "expand",
then we can translate indentation into the output pretty well, even
though each code fragment in the "source" starts in column 1.


Design: Replacing Templates
===========================
In a more traditional system, the server maintains "templates" of, e.g., HTML.
For example, a web site might widely reuse across many URLs a template that
supplies the basic HTML head, body, menu nav, etc. -- a common skeleton. The
server then "fills in" the variable parts of that template for a given
URL, possibly refering to other templates, or even a URL-specific template.

LP5 can do the same thing. Just need ability to store code that contains
unresolved references. That forms a "template", and the user of that template
supplies definitions for the unresolved references.

In some sense, this is more readable. Instead of templates residing in other
files, you "edit" a URL and you see all the source code for all the "templates"
that URL is using. Main problem is, when you edit a "foreign" chunk of code,
do you really modify that (possibly widely reused) code, or is it a copy-on-write
kind of situation, or what?

The other aspect of "normal" templates is their ability to mix in code
that, on the server side, is actually generating fragments of the page
from dynamic data. Interesting choice would be to require all dynamic
generation to happen client side and supplying data via an auxiliary
URL. Idea being that the ".html" URL stays static in the face of dynamic
data, so it never has to be downloaded more than once after a code change.
This isolates what really is dynamic in a separate URL to reduce
server load and bandwidth requirements.

Deliberate Redundancy
=====================
One faddish term that many modern programmers know is
DRY -- Don't Repeat Yourself.
Unfortunately, as with most rules about programming
(or any complex activity), this rule blah blah blah.

When using a modern screen editor or IDE, programmers often
use window "panes" in order to be able to see code from
different files (or different places in the same file)
side by side. Sometimes, the same multi-pane editor positioning crops up
repeatedly because two pieces of code are strongly
related but cannot be placed together in the source code file,
perhaps because of language constraints.

Sometimes, the problem is that a single piece of code simply
has strong relationships to two or more other pieces of code.
Software is ultimately a linear medium, like prose,
so linear proximity can only be used to express one
such relationship.

Architecture
============
After initialization, the system sits and waits for an event. Keyboard
and mouse events will invoke event handlers attached to the DOM. If we
use addEventListener, then that can effectively attach Javascript objects
to the DOM.

We could also attach objects to DOM notes directly, and
allow the browser to handle their lifetimes, so long as our own objects
don't also have references to them. However, that implies that we
will go through the DOM whenever we need to access those objects
(since the posit was that the DOM holds the only references to them).

Note that addEventListener() effectively demultiplexes all events back
to one handler (.handleEvent(Event)).
